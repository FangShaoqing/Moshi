## 〇、为什么先做服务层
手机接入的通道有很多（QQ/微信/飞书/TG……），但它们**都是同一条路**：收消息 → 她处理 → 回消息。
所以先把"她"做成一个**通道无关的服务**——之后所有通道都是插头，可并行、可替换，且这正是"在线/云端"的核心件。

## 一、架构
```
任何通道（QQ/微信/QClaw/飞书/……）→ ★ Moshi 服务层（runtime.Session）
                                          ├─ 她的人格/记忆/机制（V4 全套，规则定边界）
                                          ├─ 状态持久化（data/SHE_<seed>/，跨渠道/跨时间）
                                          ├─ 离线补日子（她不在时也在过日子；日子传染今天心情）
                                          └─ DeepSeek（只说"她的口吻"）
```

## 二、接口（moshi/server.py，只依赖标准库）
| 接口 | 用途 | 对接通道 |
|---|---|---|
| `POST /v1/chat/completions` | **OpenAI 兼容**——把 Moshi 当作"一个模型"，任何支持自定义 API 的框架可直接填这个地址 | QClaw（龙虾）/ OpenClaw 自定义后端 |
| `POST /onebot/` | OneBot v11 HTTP 回调（事件 → 快速回复 `{"reply": ...}`；配了 onebot_api 则走 API 推送） | **NapCat（QQ 小号）** |
| `POST /tick` | 定时主动："她会突然想起你"（QQ 推送需 `service.json` 配 `onebot_api`+`qq_user_id`） | QQ 推送 |
| `GET /healthz` | 健康检查 | — |

## 三、关键机制（runtime.Session）
- **一个种子 = 一个她**（相遇定格 + 日子引擎 + 持久化，与 demo 同源）；
- **跨消息状态**：她说过的、记得的、信任度/依恋/故事全在（OpenAI 兼容也保持——消息数组只是"传输"，她的状态在自己那）；
- **离线自动补日子**：每次消息前检查 `last_life_day < 今天` → 推进日子 + 缺席→依恋（她未必更想你，可能在淡）；
- 每次消息后落盘（崩溃安全）。

## 五、QQ 接入探路（进行中，下一步）
**推荐路线：NapCat（QQ 小号，OneBot v11）**——已完成服务端对接：
1. 准备一个 **QQ 小号**（别用主号；[近期 QQ 群风控收紧](https://bbs.binmt.cc/forum.php?mod=viewthread&tid=155873&page=1#pid10119525)，自用单聊低频风险可控，但小号最稳）；
2. 装 NapCat（本地、[10 分钟、无需公网 IP](https://www.cnblogs.com/28Blog/p/archive/2025/11/23)），配置 HTTP 回调指向 `http://127.0.0.1:8901/onebot`；
3. 跑 `python -m moshi.server` → QQ 小号发消息，她在 QQ 里回应。
**备选：QQ 官方机器人**（开放平台，WebSocket，官方零风险）——需你先注册探路：私聊能力是否对个人开发者开放；开放则加一个 ws 适配器（同 Session 接口，改动极小）。
